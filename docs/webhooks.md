# Webhooks

The gateway can push events to your own HTTPS endpoints. Each delivery carries a `Signature` header (an HMAC of the
body), is retried with backoff, and an endpoint that keeps failing is paused. Event names, the body and the
signature follow the reference API, so a receiver written for it works here too. Coming from 1.x? See
[Upgrading to 2.0](../CHANGELOG.md#upgrading-to-20).

Events come from the upstream's event socket (`UPSTREAM_WS_URL`), which the API process reads when `RUN_JOBS=true`.
Without `UPSTREAM_WS_URL` only `webhook.test` is sent (from the test route).

## Endpoints

All routes are under `/v1` and accept an API key or the dashboard session (see
[authentication.md](authentication.md)). Writes need a `write` key. Keys limited to specific accounts get
`403 account_not_allowed` on every webhook route, because an endpoint receives events for every account.

| Route | What it does |
|---|---|
| `GET /v1/webhooks` | List endpoints |
| `POST /v1/webhooks` | Create one: `{ url, description?, events? }`. Returns `201 { endpoint }` |
| `GET /v1/webhooks/events` | The event catalogue |
| `GET /v1/webhooks/:id` | One endpoint |
| `PATCH /v1/webhooks/:id` | Change `url`, `description`, `events` or `enabled` |
| `DELETE /v1/webhooks/:id` | Delete it and its deliveries |
| `POST /v1/webhooks/:id/test` | Queue a `webhook.test` delivery. Returns `202 { delivery }` |
| `GET /v1/webhooks/:id/deliveries` | Recent deliveries, newest first. Filters: `status`, `event`, `cursor`, `limit` |
| `POST /v1/webhooks/:id/deliveries/:deliveryId/redeliver` | Send a delivery again. Returns `202 { delivery }` |

- `url` must be `https://`. `events` is a list of event types; empty means every event.
- `events` names must come from the catalogue below; any other name (including the 1.x names) is a `400`.
- The `secret` (`whsec_...`) is generated by the gateway and stored in plaintext, because signing needs it. It is
  included in endpoint responses for the dashboard session and `write` keys only; `read` keys get the endpoint
  without it.
- `enabled: false` pauses the endpoint (`pausedReason: "manual"`). `enabled: true` resumes it and resets the
  failure counter.
- While an endpoint is paused, new events are **not** queued for it (they are dropped for that endpoint). The test
  and redeliver routes still queue a delivery (`202`); it is sent once the endpoint is enabled again, as are
  retries that were pending when it was paused.

### Event types

The catalogue accepts every event name of the reference API that is in scope here, so a subscription copied from
it validates. **Status** says whether this gateway sends the event:

- **emitted**: sent today.
- **TBC**: the OnlyFans source is known, but the upstream does not map it yet (it needs a captured frame or a
  poller). Until then such a frame may arrive as `upstream.<name>`.
- **never**: there is no source in a self-hosted gateway (the reference API's own connect flow, uploads), so it is
  accepted in a filter and never sent.

| Type | Status | Sent when | `payload` |
|---|---|---|---|
| `messages.received` | emitted | A connected account received a message | The OnlyFans message object, with `fromUser` |
| `messages.sent` | emitted | A connected account sent a message | The OnlyFans message object, with `toUser` |
| `messages.ppv.unlocked` | TBC | A fan unlocked a paid message (post unlocks arrive as `transactions.new`) | The OnlyFans notification, with `user` |
| `messages.deleted` | emitted | A message in one of the account's chats was deleted | `{ id }` (the message id, as a string) |
| `messages.liked` | TBC | A fan liked a message | `{ id }` |
| `messages.unliked` | TBC | A fan unliked a message | `{ id }` |
| `chat_queue.updated` | TBC | A mass-message queue made progress | The queue's state (`pending`, `total`, `isDone`, ...) |
| `chat_queue.finished` | TBC | A mass-message queue finished | Same as `chat_queue.updated` |
| `subscriptions.new` | TBC | A fan subscribed | The OnlyFans notification, with `user` |
| `subscriptions.renewed` | TBC | A fan renewed | The OnlyFans notification, with `user` |
| `subscriptions.expired` | TBC | A fan's subscription expired | The subscription, with `user` and `expiredAt` |
| `users.typing` | TBC | A fan is typing | `{ id }` |
| `users.online` | TBC | A fan came online | `{ fan, observed_at, ... }` |
| `users.offline` | TBC | A fan went offline | Same as `users.online` |
| `posts.liked` | TBC | A fan liked a post | The OnlyFans notification, with `user` |
| `posts.expired` | emitted | A post in the account's feed expired, not only one of its own (ours; the reference API has no such event) | `{ postId }` |
| `tips.received` | TBC | A fan tipped | The OnlyFans notification, with `amountGross`, `amountNet` and `user` |
| `transactions.new` | TBC | A new earnings transaction | The transaction (`amount`, `net_amount`, `currency`, ...) |
| `accounts.connected` | emitted | An account was connected for the first time (`connect.py`) | `{ state, progress, latestAuthAttempt }` |
| `accounts.reconnected` | emitted | An account that already had a session was connected again | Same as `accounts.connected` |
| `accounts.disconnected` | never | | |
| `accounts.session_expired` | emitted | A connected account's session expired: OF answered 401 (or 400 "Wrong user") to any call for it, and its status stays `session_expired`, sent once, until you re-connect it | Same as `accounts.connected` |
| `accounts.authentication_failed` | never | | |
| `accounts.otp_code_required` | never | | |
| `accounts.face_otp_required` | never | | |
| `media_uploads.completed` | never | | |
| `media_uploads.failed` | never | | |
| `webhook.test` | emitted | You call the test route. It ignores the endpoint's `events` filter | `{ message }` |
| `upstream.*` | emitted | Any other upstream event, as `upstream.<name>`. Subscribing to `upstream.*` covers all of them | The upstream's raw value |

`GET /v1/webhooks/events` returns the same list, with the status in each description. Payloads are built by the
upstream; amounts are OnlyFans' gross figures in cents, and the ledger behind `/v1/stats` stores them per event.

When the upstream starts mapping a TBC type, its frames move from `upstream.<name>` to the catalogue name. An
endpoint that relied on `upstream.*` for them then needs the catalogue name in its `events` filter (or an empty
filter). `upstream.*` names and contents are not a stable contract: any minor release may move one to a catalogue name
or stop sending it.

`accounts.reconnected` fires on every successful bootstrap of an account that already had a session, not only after
a disconnect or an expired session.

**Payload notes.** The payloads have the keys of the reference API's examples, but live OnlyFans frames carry fewer
of them:

- `messages.received`: observed on a subscriber-side account (a 3-day capture, docs/spec/plan-v6-ws-events.md), the
  frame carried the reference's full 42-key `fromUser` and no `replyToMessage`; creator-side frames are
  unverified. `messages.sent` was not observed; it is assumed to have no `toUser`.
- `posts.expired`: in the same capture OnlyFans sent `post_expire` for posts of other creators in the account's
  feed, at about 480 a day, so the event and its `/v1/stats` count are not limited to the account's own posts.
- `fanData.available` is `false` and the `spending` figures are zero, because the gateway does not compute fan
  spending. `fanData.last_updated_at` is the message's time. Branch on `available` before using `spending`.

Every event goes to every workspace linked to the upstream (`link-team`). `messages.received` and `messages.sent`
carry the fan's message text and profile, and `upstream.*` events carry the upstream's raw payload, which reaches every endpoint
whose `events` filter is empty. So anyone with an endpoint in a linked workspace receives that text. The gateway's
own event ledger (used for `/v1/stats`) stores no payloads.

Delivery from the upstream is **at-most-once**: there is no replay. Events are not sent when they happen while the
gateway is down or reconnecting to the upstream, or while the gateway is more than 1000 events behind, or when the
ledger insert fails; resync from the REST API when you need a complete view. A catalogued event (not `upstream.*`)
the upstream sends twice with the same id is queued once.

Run one API process with `RUN_JOBS=true`: each such process opens its own upstream socket, and events the ledger
cannot deduplicate (`upstream.*`, or sent without an id) are then queued once per process.

## The request

Every delivery is a `POST` whose body is the event envelope, with the keys in this order:

```json
{"event":"messages.received","account_id":"1001","payload":{ }}
{"event":"webhook.test","payload":{"message":"Test event from the gateway"}}
```

- `event` is the type from the table above.
- `account_id` is the account the event belongs to, as a JSON **string**. It is omitted when the event has no
  account, as for `webhook.test`.
- `payload` is the event's data (it may be `null`).

It comes with these headers:

| Header | Value |
|---|---|
| `Content-Type` | `application/json` |
| `User-Agent` | `Gateway-Webhooks` |
| `X-OFAPI-Idempotency-Key` | The event's id (`evt_...`). The same on every automatic retry and every manual redelivery |
| `Signature` | 64 lowercase hex characters: HMAC-SHA256 of the raw body (below) |

Answer with any `2xx` within 10 seconds (the deadline covers the DNS lookup too). Redirects are not followed and
count as failures.

### De-duplicating

A delivery can arrive more than once: a retry after a timeout whose request did reach you, or a redelivery. Drop
duplicates on `X-OFAPI-Idempotency-Key`. The delivery id (`whd_...`, shown in the dashboard and the deliveries API)
changes on a redelivery; the key does not. Two Test actions are two events with two keys.

- The key is **not** covered by the signature. It only de-duplicates the gateway's own retries and redeliveries;
  it does not stop a replayed request.
- A receiver that drops by key also discards a manual redelivery of an event it already acknowledged. Redeliver
  only what the receiver did not process.
- Deliveries created before 2.0, and their redeliveries, carry their `whd_...` delivery id as the key (the
  migration's backfill).

## Verifying the signature

`Signature` is the lowercase hex HMAC-SHA256 of the raw request body. The key is the UTF-8 bytes of the endpoint's
`secret`, the whole `whsec_...` string as it is (it is not base64-decoded). Verify against the raw body bytes,
before any JSON parsing, and compare in constant time.

Node:

```js
import { createHmac, timingSafeEqual } from 'node:crypto';

function verify(secret, signature, rawBody) {
  if (!/^[0-9a-f]{64}$/.test(String(signature))) return false;
  const expected = createHmac('sha256', secret).update(rawBody).digest();
  return timingSafeEqual(Buffer.from(signature, 'hex'), expected);
}
// verify(process.env.WEBHOOK_SECRET, req.headers['signature'], rawBodyBuffer)
```

Python:

```python
import hashlib
import hmac

def verify(secret: str, signature: str, raw_body: bytes) -> bool:
    expected = hmac.new(secret.encode("utf-8"), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected.encode(), (signature or "").encode())
```

The signature covers the body only. There is no timestamp, so there is **no replay window**: a captured request
verifies forever. Keep endpoints on `https://`, and de-duplicate on `X-OFAPI-Idempotency-Key`.

## Retries and pausing

- A failed attempt (non-2xx, timeout, connection error) is retried after **30 s, 2 m, 10 m, 1 h, then 6 h**. After
  `WEBHOOK_MAX_ATTEMPTS` attempts (6) the delivery is `failed`.
- Each `failed` delivery adds one to the endpoint's `consecutiveFailures`; any `2xx` resets it to 0. At
  `WEBHOOK_PAUSE_AFTER` (20) the endpoint is disabled with `pausedReason: "failures"`. Re-enable it with
  `PATCH { "enabled": true }`.
- Redeliver creates a **new** delivery with a new id and `replayOf` set to the original. It keeps the original's
  `eventId`, so it carries the same `X-OFAPI-Idempotency-Key`.
- `dropped` deliveries were pending 1.x deliveries that the 2.0 migration cancelled; they are never sent.
- Finished deliveries (`succeeded`, `failed` or `dropped`) are deleted after `WEBHOOK_RETENTION_DAYS` days (7).
  Pending ones are kept, so a long-paused endpoint still gets its queued deliveries.

Deliveries are sent by the API process when `RUN_JOBS=true`, up to 5 at a time. One worker process is the supported
setup. Each claimed delivery is leased for about a minute, and the attempt is recorded only if the lease is still
the worker's own, so an accidental second process cannot double-count or overwrite. An attempt only counts once it
finishes, so a restart in the middle of a delivery delays it by about a minute instead of using up an attempt.

### Blocked targets

Endpoint URLs must be `https://`. Before each attempt the gateway resolves the host and refuses link-local
addresses (`169.254/16`, including cloud metadata, and `fe80::/10`) and private, loopback or special-purpose ones
(`0/8`, `10/8`, `100.64/10`, `127/8`, `172.16/12`, `192.0.0/24`, `192.168/16`, `198.18/15`, `224/4`, `240/4`,
`::`, `::1`, `64:ff9b::/96`, `2002::/16`, `fc00::/7`). Such an attempt fails with an error in `lastError`. The
connection itself can still resolve the name again (DNS rebinding is not prevented).

## Trying it locally

`ALLOW_HTTP_WEBHOOKS=true` allows plain `http://` URLs and private or loopback hosts (for example a receiver on
the same Docker network). Link-local addresses stay blocked. Use it only in development or on a trusted network.

```sh
# API with ALLOW_HTTP_WEBHOOKS=true in .env, then create an endpoint for http://localhost:4100/hook
WEBHOOK_SECRET=whsec_... tsx apps/api/src/db/webhook-receiver.ts   # listens on :4100, logs "signature ok"
curl -X POST http://localhost:4000/v1/webhooks/$ID/test -H "authorization: Bearer $KEY"
```

Start the receiver with `FAIL=1` to answer `500` and watch the retries. To see the endpoint pause quickly, set
`WEBHOOK_MAX_ATTEMPTS=1` and `WEBHOOK_PAUSE_AFTER=3`.
