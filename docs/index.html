Gateway

A self-hosted API gateway and dashboard for a creator-platform service, with the upstream service included.

Each workspace creates its own scoped API keys and calls /v1/{account}/.... Gateway checks the key, forwards the call with one upstream bearer token, and records it. Your upstream stays private, your users never see its credential, and you get logs, usage, a playground and an API reference without building them.

What you get

Everything between your users and the upstream, ready on first start.

Scoped API keys

gk_ keys, shown once and stored as SHA-256 hashes. A read key may only GET and HEAD, a write key any method, and each key can be limited to a list of accounts. Changes and revocation apply on the next request.

Proxy

/v1/{account}/<path> reaches the upstream with one bearer token your users never see. Status, content-type, retry-after and x-ratelimit-* come back as sent; a successful JSON body arrives as {"data": …, "_meta": {}}, errors unchanged. 120 requests a minute per key by default.

Logs with redaction

Every /v1 request made with an API key, and the playground's calls, with status, latency, key and account. Credential headers are never stored and secret-looking fields are masked. Bodies are kept for failed requests, logs for 14 days.

Usage

Requests and errors per day, broken down by key, account or endpoint, with a CSV export.

Playground

Pick an operation and an account, edit parameters and body, send, and copy the curl. It uses your dashboard session, so no key is pasted into the browser.

Merged OpenAPI reference

/openapi.json holds Gateway's own routes plus the upstream's operations rewritten to /v1/{account}/..., and /docs renders it as an interactive reference.

Webhooks and live events

Signed deliveries to your HTTPS endpoints, with retries and redelivery. The same events stream over the /v1/ws WebSocket and into the dashboard's live feed.

Chat analytics

Backfill an account's chats and sales, then read reply time, reply SLA, openers, scripts, conversations and revenue, per account and per day.

Workspaces

Keys, logs and usage belong to one workspace. Sign-up is open, but a workspace reaches the upstream only after the operator links it, and every linked workspace sees every connected account: run one deployment per operator.

How it fits

Clients call Gateway with a gk_ key. Gateway forwards /v1/{account}/<path> to the upstream's /of/<path> with Authorization: Bearer $UPSTREAM_TOKEN and never forwards the client's own credentials. The bundled upstream in services/upstream holds each account's session and proxy, and streams its events back over one WebSocket, which Gateway fans out to webhooks and /v1/ws clients. Any service that answers the same calls can replace it; the README lists the contract.

 client (curl, script, browser)
        │  HTTPS · Authorization: Bearer gk_... · REST and /v1/ws
        ▼
 ┌──────────────┐  http   ┌────────────────────────┐  Bearer UPSTREAM_TOKEN  ┌────────────────────────┐
 │ Caddy (TLS)  │───────▶ │ Gateway :4000          │───────────────────────▶ │ upstream :8000         │
 └──────────────┘         │ API + dashboard        │◀──── events (/ws) ──────│ services/upstream      │
                          │ webhooks, /v1/ws       │                         │ OF sessions, proxies   │
                          └───────────┬────────────┘                         └───────────┬────────────┘
                                      │                                                  │ one proxy
                          ┌───────────▼────────────┐                                     │ per account
                          │ Postgres 17            │                                     ▼
                          │ keys, sessions, logs,  │                                     OF
                          │ event ledger           │
                          └────────────────────────┘

Tutorial: from zero to your first call

The commands below come from getting-started.md and the deploy guide. Locally the API is on http://localhost:4000 and the dashboard on http://localhost:5173; on a VPS both are your PUBLIC_URL.

  1. Run it

    Locally

    You need Node 22.12 or newer, pnpm 10 and Docker. For BETTER_AUTH_SECRET, openssl rand -base64 32 works; .env.example fills in the rest for local use.

    pnpm install
docker compose up -d     # Postgres 17 on 127.0.0.1:5434, plus a gateway_test database
cp .env.example .env     # set BETTER_AUTH_SECRET, and UPSTREAM_TOKEN=dev-upstream-token
pnpm db:migrate
pnpm dev                 # API on http://localhost:4000, dashboard on http://localhost:5173

    Then start an upstream on port 3001 (the default UPSTREAM_URL) in a second terminal. The fake one the tests use needs no real account and serves one account with id 1; the bundled one in services/upstream talks to the platform:

    UPSTREAM_TOKEN=dev-upstream-token pnpm --filter @gateway/api exec tsx test/fake-upstream.ts
# or, for real accounts:
docker compose --profile upstream up -d --build upstream

    For events (webhooks, /v1/ws, live stats), add UPSTREAM_WS_URL=ws://localhost:3001/ws to .env and restart pnpm dev. Both upstreams serve it.

    On a VPS

    You need a Docker VPS with 2 GB RAM or more, a DNS record for your hostname, and ports 80 and 443 open. Fill in four values in deploy/.env: PUBLIC_URL (your https:// hostname, no trailing slash), POSTGRES_PASSWORD (openssl rand -hex 24), BETTER_AUTH_SECRET (openssl rand -base64 32) and UPSTREAM_TOKEN (openssl rand -hex 32; letters, digits and -._~ only). The rest defaults to the bundled upstream. Set STATIC_PARAM, OF's static signing parameter, there too, or pass it per account when you connect one (step 3).

    git clone https://github.com/BlackPhoenixSlo/gateway.git /opt/gateway
cd /opt/gateway/deploy
cp .env.example .env && chmod 600 .env
docker compose up -d
curl -fsS https://gw.example.com/healthz

    The first run builds the images and takes a few minutes. Migrations run on every start and Caddy fetches a certificate on first boot. The deploy guide also covers updates, backups, the firewall and running behind a Cloudflare Tunnel.

  2. Sign up and get your workspace linked

    Open the dashboard and register, then open the verification link from your email. Without SMTP the link is printed in the API log (docker compose logs gateway on a VPS). This creates your workspace. Until the operator links it, calls that would reach the upstream fail with 409 team_not_linked. Copy the workspace slug from Settings, then link it:

    pnpm --filter @gateway/api link-team <workspace-slug>                    # locally
docker compose exec gateway node dist/db/link-team.js <workspace-slug>   # on the VPS, from /opt/gateway/deploy

    Running it again is harmless. Link only workspaces you trust: every linked workspace sees every connected account.

  3. Connect an account

    With the fake upstream, account 1 is already there; skip to step 4. Otherwise copy a cURL from Chrome: DevTools → Network → a request to onlyfans.com/api2/v2/… → Copy as cURL (bash). It must carry the cookies as -b '…'. On Accounts, press Connect account, paste it, add a nickname if you like, and a proxy URL for that account (http://user:pass@host:port or socks5h://…; without one the account connects from the server's own IP). Gateway hands the cURL to the upstream and never stores it in the request log. Or connect from the shell:

    docker compose exec -T upstream python connect.py --nickname Main --proxy-url socks5h://user:pass@host:port < curl.txt

    Either way, the upstream needs OF's static signing parameter: STATIC_PARAM in its environment (deploy/.env on a VPS, applied by docker compose up -d; locally STATIC_PARAM=… docker compose --profile upstream up -d upstream), or --static-param <value> added to the shell command.

    The account then shows up on Accounts with its status. A session_expired account needs a fresh cURL.

  4. Create an API key

    On API keys, press Create key and give it a name, a scope and, if you like, a list of allowed account ids (empty means every account). See authentication.md for the details.

    • read allows GET and HEAD only; anything else gets 403 insufficient_scope.
    • write allows every method.
    • Each key may make 120 requests a minute (KEY_RATE_LIMIT_PER_MIN); over that you get 429 rate_limited.

    The secret is shown once, so copy it now:

    export API_KEY=gk_...

  5. Make your first call

    curl -H "Authorization: Bearer $API_KEY" http://localhost:4000/v1/whoami
curl -H "Authorization: Bearer $API_KEY" http://localhost:4000/v1/accounts
export ACCOUNT_ID=123    # an id from /v1/accounts (1 with the fake upstream)
curl -H "Authorization: Bearer $API_KEY" http://localhost:4000/v1/$ACCOUNT_ID/me
# {"data": { ...the upstream's body... }, "_meta": {}}

    /v1/whoami shows the workspace, the key's scope and its allowlist; /v1/accounts lists the accounts the key may use. Anything under /v1/{account}/ is forwarded to the upstream for that account. A successful JSON answer comes back wrapped in {"data": …, "_meta": {}}, plus "_pagination": {"next_page": …} when there is a next page; the upstream's errors come back unchanged. Gateway's own errors look like { "error": { "code": "...", "message": "...", "requestId": "req_..." } }, and every response carries an x-request-id header.

  6. Try the playground

    Open Playground, pick an operation and an account, fill in the parameters and body, and press Send. It runs on your dashboard session, so no key is needed in the browser, and its account calls are logged with the key "Dashboard". Copy the curl snippet (it uses $API_KEY) when you want the same call in a script. The full reference is at /docs, and the spec at /openapi.json; neither needs a login.

  7. Read logs and usage

    Logs lists the /v1 requests made with an API key and the playground's calls (not the dashboard's own polling); open a row for its headers and bodies, or Open in playground to send it again. Usage charts requests and errors per day by key, account or endpoint. Bodies are stored only for failed requests (status 400 and up) unless you set LOG_BODIES to all or none, and logs are kept for LOG_RETENTION_DAYS days (14). Set them in .env; on a VPS, add them to the gateway service's environment in deploy/docker-compose.yml, which lists its variables one by one.

  8. Subscribe to webhooks and live events

    Events come from the upstream's event socket, UPSTREAM_WS_URL (the deploy .env already points it at the bundled upstream). On Webhooks, press Add endpoint, enter an https:// URL and the events you want (none means every event), then Send test event. The Live events card shows events as they arrive, whether or not an endpoint gets them. Or create the endpoint with a write key (keys limited to some accounts get 403 account_not_allowed on webhook routes):

    curl -X POST http://localhost:4000/v1/webhooks \
  -H "Authorization: Bearer $API_KEY" -H "content-type: application/json" \
  -d '{"url": "https://example.com/hook", "events": ["messages.received", "messages.sent"]}'
curl -X POST http://localhost:4000/v1/webhooks/$ID/test -H "Authorization: Bearer $API_KEY"   # $ID from the response

    Each delivery is a POST of {"event", "account_id", "payload"} with a Signature header, the hex HMAC-SHA256 of the raw body keyed with the endpoint's whsec_... secret, and an X-OFAPI-Idempotency-Key to drop duplicates on. Failed attempts are retried after 30 s, 2 m, 10 m, 1 h and 6 h, and an endpoint that keeps failing is paused. webhooks.md has the event list and verification code for Node and Python. To try it locally, set ALLOW_HTTP_WEBHOOKS=true in .env (otherwise only https:// public hosts are accepted), run WEBHOOK_SECRET=whsec_... pnpm --filter @gateway/api exec tsx src/db/webhook-receiver.ts and point an endpoint at http://localhost:4100/hook; it logs "signature ok" for each delivery.

    To get the same events over a socket instead, connect to /v1/ws (realtime.md). In a browser, use a read key limited to the accounts the page needs:

    const ws = new WebSocket('wss://gw.example.com/v1/ws', ['bearer', 'bearer.' + apiKey]);
ws.onmessage = (m) => console.log(JSON.parse(m.data));
// {"event":"messages.received","account_id":"1001","payload":{...}}

  9. Run analytics and read the stats

    This needs a real, active account. On Accounts, pick 30, 90 or 180 days and press Run analytics. Gateway claims the account for your workspace and reads its chats, messages and transactions through the upstream in the background; the row shows Running… N chats, M messages, then Done · view Stats. Long ranges take hours at the per-hour request cap, one account runs at a time, and restarting the API ends a run in flight (the rows already stored stay).

    Then read Stats (reply time, SLA, openers, scripts, fans), Conversations (each fan's thread, with CSV export) and Revenue. The same data is on the API:

    curl -X POST http://localhost:4000/v1/stats/backfill \
  -H "Authorization: Bearer $API_KEY" -H "content-type: application/json" \
  -d '{"accountId": 123, "days": 30}'
curl -H "Authorization: Bearer $API_KEY" "http://localhost:4000/v1/stats/backfill?accountId=123"
curl -H "Authorization: Bearer $API_KEY" "http://localhost:4000/v1/stats/metrics/reply_time?groupBy=day"
curl -H "Authorization: Bearer $API_KEY" "http://localhost:4000/v1/stats/revenue?from=2026-09-01&to=2026-09-30"

    Live messages.received, messages.sent and messages.deleted events keep the stored messages current between runs. Set STATS_REFRESH_HOUR_UTC (0 to 23) for a daily refresh of each claimed account and an hourly poll of recent sales: in .env locally; on a VPS, add it to the gateway service's environment in deploy/docker-compose.yml and run docker compose up -d to recreate the container. See analytics-backfill.md for the command-line backfill and analytics.md for every metric's formula.

    Every metric is marked verified: false: the formulas are built and tested, but not yet checked by hand against the platform or another tool's export.
